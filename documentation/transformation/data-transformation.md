
# Stage 3: Data Load Documentation

**Project:** VistaBalayan: A Web-Based Tourism Data Analytics and Decision Support System for Visitor Monitoring in Balayan, Batangas

**Pipeline Stage:** Stage 3 – Data Load

## Objective

The objective of Stage 3 is to load the approved transformed VistaBalayan datasets into a designated reporting database. This stage ensures that the loaded records are complete, accurate, and traceable, making them available for tourism data reporting, visitor monitoring, accommodation analysis, and historical data analysis.

The Load Stage follows the approved output of the Transformation Stage and uses scheduled batch processing only. It does not perform data extraction, cleaning, or transformation.

## 1. Load Source and Target Specification

### 1.1 Load Input

The Load Stage receives the cleaned, standardized, and validated CSV datasets generated by the Transformation Stage. These files are the final outputs of the transformation process and serve as the input for loading into the target database.

**Input Directory:** `pipeline/transformed/`

The Transformation Stage produces the following datasets:

| **Transformed File** | **Target Table** |
|---|---|
| `establishments.csv` | `reporting.establishments` |
| `visitor_reports.csv` | `reporting.visitor_reports` |
| `accommodation_reports.csv` | `reporting.accommodation_reports` |
| `room_occupancy_details.csv` | `reporting.room_occupancy_details` |

The files contain the transformed records from the four original VistaBalayan datasets. Their column names and data types must follow the approved Transformation Stage data contract.

The Load Stage must also receive the transformation metadata and validation results to establish the origin and approval status of each batch.

| **Batch Identifier** | **Specification / Example** |
|---|---|
| Transformation Run ID | `TRN_YYYYMMDD_HHMMSS` |
| Extraction Run ID | Referenced through the Transformation Stage `parent_run_id` |
| Batch ID | `BATCH_<run timestamp>` |
| Batch Window | Inherited from the Extraction Stage handover |
| Handover Status | `APPROVED` |
| Input Format | CSV |

The Transformation Stage generates its batch identifier from the transformation run timestamp. The actual run ID, batch ID, and batch window must be obtained from the corresponding transformation metadata rather than assigned independently by the Load Stage.

The extraction run identifier must also be retained for lineage. If the documented placeholder `EXT_FROM_STAGE1_HANDOVER` is used because the actual extraction run ID was not supplied, the upstream identifier must be corrected before production handover.

Only batches with an `APPROVED` transformation decision may proceed to loading. Batches marked `MANUAL_REVIEW`, `REJECTED`, or `FAILED` must be held and must not be loaded.

### 1.2 Target System

| **Item** | **Specification** |
|---|---|
| Target System | VistaBalayan Reporting Database |
| Purpose | Store validated tourism datasets for reporting, visitor monitoring, and historical analysis |
| Database Management System | PostgreSQL |
| Target Database | `vistabalayan_warehouse` (proposed) |
| Target Schema | `reporting` |
| Audit Schema | `pipeline_audit` (proposed) |
| Processing Type | Batch Processing |

The proposed reporting database will serve as the destination of the approved transformed datasets. It will provide a centralized location for storing tourism records that can be accessed by reporting and analytical processes.

The reporting database will be separate from the operational VistaBalayan database used by the web application. This separation prevents the ETL loading process from directly modifying operational tourism records while providing a dedicated location for analytical data.

The target database and schemas are proposed components of the Load Stage and must be configured before implementation.

### 1.3 Load Method

| **Item** | **Specification** |
|---|---|
| Load Technology | Python and PostgreSQL SQL |
| Proposed Load Script | `pipeline/load.py` |
| Load Frequency | Daily batch processing |
| Proposed Load Schedule | After successful Transformation Stage validation |
| Load Method | Bulk loading using PostgreSQL COPY |
| Write Strategy | Transaction-controlled batch loading |
| Expected Record Count | Based on the approved Transformation Stage metadata |
| Expected Completion Time | Determined by dataset volume and loading performance |

The loading process begins only after the Transformation Stage has successfully completed its validation checks and approved the batch for handover.

The proposed Python loading script will read the four transformed CSV files from `pipeline/transformed/` and transfer their records into the corresponding PostgreSQL target tables.

The loading process will first verify the presence of the required files, expected columns, and record counts against the transformation metadata. The CSV records will then be loaded into temporary staging tables using PostgreSQL COPY. After successful validation, the records will be transferred to their corresponding reporting tables using SQL operations.

Database transactions will be used to maintain consistency during loading. If a critical loading operation or validation check fails, the transaction must be rolled back to prevent incomplete or partially updated target data.

The Load Stage will not repeat the cleaning, standardization, or business transformation procedures already completed in Stage 2.

### 1.4 Load Scope

The Load Stage covers the four transformed datasets produced by the Transformation Stage. The loading order follows their existing primary-key and foreign-key relationships, ensuring that parent records are available before dependent records are loaded.

| **Load Order** | **Target Table** | **Dependency** |
|---|---|---|
| 1 | `reporting.establishments` | None |
| 2 | `reporting.visitor_reports` | `reporting.establishments` |
| 3 | `reporting.accommodation_reports` | `reporting.establishments` |
| 4 | `reporting.room_occupancy_details` | `reporting.accommodation_reports` |

The expected record count for each transformed dataset will be based on the approved Transformation Stage metadata. The original extraction counts will not automatically be used as the expected loading counts because records may have been modified, deduplicated, or rejected during transformation.

The following extraction counts provide the initial reference for the four datasets:

| **Dataset** | **Stage 1 Extracted Records** |
|---|---:|
| `establishments` | 38 |
| `visitor_reports` | 2,400 |
| `accommodation_reports` | 1,857 |
| `room_occupancy_details` | 5,938 |

These figures represent the previously documented extraction results, not guaranteed final loading counts. The actual number of records loaded must match the approved transformed output for each batch.

The loading process must preserve the existing primary keys and foreign-key relationships, including:

- `visitor_reports.establishment_id` referencing `establishments.id`
- `accommodation_reports.establishment_id` referencing `establishments.id`
- `room_occupancy_details.accommodation_report_id` referencing `accommodation_reports.id`

Each batch must finish after the approved transformation output becomes available and before the next scheduled pipeline execution. Actual completion time will depend on the number of records, database availability, and system resources.

### 1.5 Limitations and Assumptions

- Only approved CSV datasets produced by the Transformation Stage are accepted for loading.
- The transformed files must be available in `pipeline/transformed/` before the loading process begins.
- The transformation run ID, batch ID, batch window, record counts, and validation results must be provided through the Transformation Stage handover metadata.
- The Load Stage must not directly retrieve records from the operational PostgreSQL source database.
- The Load Stage must not repeat extraction, cleaning, standardization, or business transformation operations.
- The proposed PostgreSQL reporting database must be available before loading begins.
- The loading account must have permission to connect to the target database, read the transformed CSV files, write to the reporting tables, use temporary staging tables, and record load audit information.
- The loading account must not have unnecessary administrative privileges or permission to modify the operational source database.
- Database credentials must be stored securely using environment variables and must not be included in the project repository.
- Loading may be affected by database connection failures, storage limitations, database locks, permission restrictions, or large data volumes.
- Missing transformed files must not automatically be treated as empty datasets.
- Zero-row datasets may be accepted only when their record counts are confirmed by the approved transformation metadata.
- Primary keys, foreign keys, column names, and data types must remain consistent with the Transformation Stage data contract.
- Duplicate identifiers and incompatible data types must be rejected or flagged rather than silently inserted.
- The loading process must retain batch information, record counts, execution status, validation results, and encountered errors for traceability.
- The proposed target database, loading script, database role, and loading schedule must be verified and configured before implementation.
